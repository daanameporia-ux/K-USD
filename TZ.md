## 0. Суть продукта

Клиент в Telegram покупает USDT за рубли: вводит сумму, получает QR-код и ссылку НСПК (СБП), платит, платёжный сервис присылает callback, клиенту на внутренний баланс зачисляются USDT по курсу Rapira с индивидуальной наценкой. С баланса клиент выводит USDT в сети TRC-20 или BEP-20; выводы вручную исполняет оператор и вносит хэш транзакции, система проверяет хэш в блокчейне.

Интерфейсы:

| Интерфейс | Для кого | Что это |
|---|---|---|
| Бот (команды и кнопки) | клиент | полный клиентский функционал в чате |
| Клиентский Mini App | клиент | тот же функционал в веб-интерфейсе внутри Telegram |
| Админка в браузере | админ, оператор | вход по логину, паролю и TOTP |
| Админский Mini App | админ, оператор | та же админка, открытая внутри Telegram, вход по Telegram-аккаунту |

Админка в браузере и админский Mini App — **одно и то же фронтенд-приложение** с двумя способами входа.

### Главные требования к качеству

1. **Безопасность денег**: ни при каких гонках, повторах callback, двойных нажатиях или падениях процесса нельзя зачислить или списать средства дважды либо уйти в минус.
2. **Устойчивость**: ошибка в обработке одного сообщения или запроса не роняет сервис; после рестарта всё продолжает работать с того же места.
3. **Тесты**: каждая бизнес-функция покрыта тестами (раздел 16). Этап не считается сделанным, пока его тесты не зелёные.

### Жёсткие ограничения

- **Никаких готовых библиотек для Telegram-ботов** (aiogram, python-telegram-bot, pyTelegramBotAPI, telethon, pyrogram и т. п.). Только собственный HTTP-клиент к `https://api.telegram.org/bot<TOKEN>/<method>`.
- Библиотеки общего назначения разрешены (HTTP-клиент, ORM, генерация QR, TOTP, хэши).
- Все денежные расчёты — `Decimal`, никогда `float`.
- Тексты бота и интерфейсов — на русском. Код, идентификаторы, комментарии — на английском.

## 1. Стек

**Backend**
- Python 3.12, FastAPI, uvicorn
- SQLAlchemy 2.x (async) + asyncpg, Alembic
- PostgreSQL 16
- httpx (Telegram, Rapira, блокчейны, провайдер)
- pydantic v2 + pydantic-settings
- argon2-cffi (пароли), pyotp (TOTP), segno (QR-картинка), pycryptodome (keccak для EIP-55)
- structlog (JSON-логи)

**Frontend**
- React 18 + TypeScript + Vite, два приложения: `client` и `admin`
- Минимум зависимостей: react-router, собственный тонкий fetch-клиент. Без тяжёлых UI-китов.
- Стили — простой CSS с переменными темы Telegram (`--tg-theme-*`), светлая и тёмная тема
- Telegram WebApp JS подключается скриптом `https://telegram.org/js/telegram-web-app.js`

**Инфраструктура**
- Docker Compose: `caddy` (автоматический HTTPS), `app`, `postgres`, `backup`
- Сервис работает **в одном экземпляре** (один процесс `app`). Redis не нужен. Это допущение зафиксировано: планировщик и rate-limit живут в процессе и в БД.

**Качество**
- pytest, pytest-asyncio, respx, hypothesis, coverage
- ruff (lint + format), mypy (strict для `app/domain` и `app/services`)
- vitest + tsc для фронтенда
- GitHub Actions: lint, типы, тесты backend на реальном PostgreSQL, сборка фронтенда

## 5. Слой Telegram (собственная реализация)

### 5.1. HTTP-клиент `telegram/client.py`
Методы (минимум): `getMe`, `getUpdates`, `setWebhook`, `deleteWebhook`, `sendMessage`, `editMessageText`, `editMessageReplyMarkup`, `deleteMessage`, `sendPhoto` (multipart, байты PNG), `answerCallbackQuery`, `setMyCommands`, `setChatMenuButton`.

Требования:
- один общий `httpx.AsyncClient` с таймаутами (connect 5 с, read 35 с для long polling, 15 с для остальных);
- ответ `ok=false` превращается в типизированное исключение `TelegramApiError(code, description, retry_after)`;
- `429` — ждать `parameters.retry_after` и повторить (до 3 раз);
- сетевые ошибки и `5xx` — повтор с экспоненциальной задержкой (до 3 раз);
- `403` (бот заблокирован пользователем) — пометить `users.bot_blocked = true`, не падать;
- «message is not modified» при редактировании — игнорировать;
- токен бота никогда не попадает в логи (URL маскируется);
- `parse_mode=HTML`, все пользовательские данные экранируются функцией `escape_html`.

### 5.2. Получение апдейтов
- **Webhook** (прод): `POST /tg/webhook`. Проверять заголовок `X-Telegram-Bot-Api-Secret-Token` (сравнение через `hmac.compare_digest`), при несовпадении — `403`. Отвечать `200` сразу, обработку запускать фоновой задачей. При старте приложение само вызывает `setWebhook` с `allowed_updates=["message","callback_query","my_chat_member"]`.
- **Polling** (dev): цикл `getUpdates` с `timeout=30`, перед стартом `deleteWebhook`.
- Дедупликация по `update_id` через таблицу `tg_updates` (вставка с `ON CONFLICT DO NOTHING`; если строка уже была — апдейт пропускается).
- Апдейты одного пользователя обрабатываются **последовательно** (блокировка по `tg_id` в процессе), разных — параллельно.
- Любое исключение в хендлере ловится, логируется с `update_id`, пользователю уходит «Что-то пошло не так, попробуйте ещё раз». Процесс не падает.

### 5.3. Роутер и FSM
- Собственный роутер: регистрация хендлеров по команде, по тексту кнопки, по префиксу `callback_data`, по состоянию FSM.
- Состояние диалога хранится в `fsm_states`. Команды `/start` и `/cancel` сбрасывают состояние из любого места.
- `callback_data` — короткие строки вида `ord:confirm:<id>`; любой id из callback проверяется на принадлежность текущему пользователю.
- Бот работает только в личных чатах; сообщения из групп игнорируются (кроме служебного чата, куда бот только пишет).

### 5.4. Очередь исходящих уведомлений
Уведомления, порождённые не действием самого пользователя (оплата прошла, вывод исполнен, алерты сотрудникам), кладутся в `notifications_outbox` в той же транзакции, что и бизнес-изменение, и отправляются фоновой задачей с повторами. Так уведомление не теряется при сбое Telegram и не откатывает деньги.

## 6. Клиентский бот

### 6.1. Команды и меню
`/start`, `/buy`, `/balance`, `/withdraw`, `/history`, `/help`, `/cancel`, `/app`. Для сотрудников дополнительно `/admin`.
Команды регистрируются через `setMyCommands`. Кнопка меню чата (`setChatMenuButton`) открывает клиентский Mini App.

Главное меню — reply-клавиатура: «💵 Купить USDT», «👛 Баланс», «📤 Вывести», «🧾 История», «🆘 Поддержка», плюс кнопка открытия Mini App.

### 6.2. Регистрация (заглушка KYC)
1. `/start` от нового `tg_id` → создаётся `users` со статусом `registering`.
2. Бот показывает приветствие и кнопку «Пройти регистрацию».
3. По нажатию вызывается `KycProvider.start(user)`. Реализация `StubKycProvider` сразу возвращает «пройдено».
4. Пользователь получает `status=active`, `kyc_status=passed`, `markup_pct = default_markup_pct`, `registered_at = now()`.

Интерфейс в `kyc/base.py`:
```python
class KycProvider(Protocol):
    async def start(self, user: User) -> KycStep: ...          # что показать пользователю
    async def handle_input(self, user: User, update: Update) -> KycStep: ...
    async def is_passed(self, user: User) -> bool: ...
```
Весь клиентский функционал закрыт проверкой `status == active and kyc_status == passed`. Блок написать так, чтобы многошаговую анкету можно было добавить без переписывания остального кода. Описать расширение в `docs/KYC.md`.

Тот же шаг регистрации должен работать и в Mini App (экран «Регистрация» с одной кнопкой).

### 6.3. Покупка USDT
1. «Купить USDT». Предварительные проверки, каждая со своим понятным текстом отказа:
   - пользователь активен; `purchases_enabled`; `can_create_orders`;
   - нет активной заявки (если есть — показать её);
   - не превышены лимиты частоты и кулдаун (раздел 9);
   - курс свежий (раздел 7.1).
2. Бот: «Введите сумму в рублях, от {min} до {max}. Только целое число, без копеек».
3. Валидация ввода:
   - допускаются цифры и пробелы-разделители (`10 000` → 10000);
   - наличие `.` или `,`, букв, минуса → «Сумма должна быть целым числом рублей, без копеек»;
   - вне лимитов → сообщение с допустимым диапазоном.
4. Предпросмотр: сумма, курс, комиссия сервиса в % и в ₽, итог в USDT. Кнопки «Подтвердить» и «Отмена».
5. По «Подтвердить» — создание заявки (раздел 7.2). Курс для расчёта берётся **заново в момент подтверждения**; если итог в USDT отличается от показанного в предпросмотре — показать обновлённый предпросмотр и попросить подтвердить ещё раз.
6. Клиенту отправляется фото QR (PNG, сгенерирован из `qr_url`) с подписью: номер заявки, сумма, сколько USDT будет зачислено, срок действия; inline-кнопки «Оплатить» (URL = `qr_url`) и «Отменить заявку».
7. Финал:
   - оплата → сообщение «Оплата получена, зачислено X USDT, баланс Y»; сообщение с QR редактируется (убираются кнопки);
   - истечение → «Заявка истекла»;
   - отмена клиентом → «Заявка отменена».

### 6.4. Баланс
Доступно, в обработке (hold), итого куплено, итого выведено.

### 6.5. Вывод
1. Проверки: `withdrawals_enabled`, пользователь активен, доступный баланс ≥ `withdraw_min_usdt`.
2. Выбор сети: TRC-20 (комиссия 4 USDT) или BEP-20 (комиссия 2 USDT).
3. Ввод адреса, валидация (раздел 8.3), проверка по чёрному списку.
4. Ввод суммы списания. Число с точностью до 2 знаков, кнопка «Вывести всё». Проверки: ≥ `withdraw_min_usdt`, ≤ доступного баланса.
5. Предпросмотр: сеть, адрес, списывается `amount`, комиссия `fee`, **к получению `amount − fee`**. Отдельной строкой предупреждение про правильность сети.
6. Подтверждение → создаётся вывод, средства уходят в hold.
7. Пока статус `pending`, клиент может отменить вывод (возврат из hold).
8. Финал: исполнено (хэш + ссылка на эксплорер) или отклонено (причина, средства возвращены).

### 6.6. История
Последние операции (покупки и выводы) постранично по 5, inline-кнопки «Назад» и «Вперёд». В каждой: номер, дата (МСК), сумма, статус.

### 6.7. Поддержка
Текст с контактом поддержки из настройки `support_contact`.

## 7. Курс и заявки на покупку

### 7.1. Сервис курса
- Источник: `GET {RATE_SOURCE_URL}`. Формат **сверен с живым ответом 11.11.2026**:
  ```json
  {"data":[{"symbol":"USDT/RUB","open":87.11,"high":87.12,"low":85.85,"close":86.37,"chg":-0.00861968,"change":-0.74,"fee":0,"lastDayClose":87.12,"usdRate":1,"baseUsdRate":0.01157675,"askPrice":86.38,"bidPrice":86.37,"baseCoinScale":2,"coinScale":2,"quoteCurrencyName":"Tether","baseCurrency":"RUB","quoteCurrency":"USDT"}, "..."],
   "code":0,"message":"SUCCESS","totalPage":null,"totalElement":null,"isWorking":1}
  ```
  Берётся элемент с `symbol == "USDT/RUB"` (искать именно по `symbol`: поля `baseCurrency` и `quoteCurrency` у источника перепутаны местами, на них не опираться). Курс покупки — поле `askPrice`. Ответ считается валидным только при `code == 0` и `isWorking == 1`. Имя поля вынести в настройку `rate_field` (варианты `askPrice`, `bidPrice`, `close`).
- Числа из JSON парсить в `Decimal` через строку (`parse_float=Decimal`), не через `float`.
- Фоновая задача обновляет курс каждые `rate_ttl_seconds` и пишет в `rates`. Запросы пользователей никогда не ходят в Rapira синхронно — только читают последний сохранённый курс.
- Курс невалиден, если: значение ≤ 0, элемент не найден, ответ не разобран, возраст больше `rate_max_age_seconds`.
- Защита от скачка: если новый курс отличается от предыдущего валидного больше чем на `rate_jump_guard_pct` %, он **не применяется**, сотрудникам уходит алерт. Админ может подтвердить его вручную либо задать `manual_rate`.
- Если задан `manual_rate`, используется он, источник помечается `manual`.
- Нет валидного курса → покупки недоступны, клиенту: «Покупка временно недоступна, попробуйте через несколько минут»; сотрудникам — алерт (не чаще раза в 10 минут).

### 7.2. Расчёт и создание заявки
Формула (наценка — это комиссия с суммы, как в примере заказчика):
```
usdt_amount = ROUND_DOWN( amount_rub × (1 − markup_pct / 100) / rate , 2 знака )
margin_rub  = amount_rub × markup_pct / 100
```
Контрольный пример: 1000 ₽, наценка 5 %, курс 100 → **9.50 USDT**, маржа 50 ₽.

Функция расчёта — чистая, в `domain/pricing.py`, без I/O.

Создание заявки — одна транзакция:
1. `SELECT ... FOR UPDATE` строки пользователя.
2. Повтор всех проверок из 6.3 п. 1 (между предпросмотром и подтверждением состояние могло измениться).
3. Если передан `idempotency_key` и заявка с ним уже есть — вернуть её.
4. Вставка `orders` со статусом `creating`, `expires_at = now + order_ttl_minutes`.
5. Коммит. Затем, **вне транзакции**, вызов `PaymentProvider.create_qr(...)`.
6. Успех → `status=pending`, сохранить `provider_payment_id`, `qr_url`. Ошибка или таймаут провайдера → `status=failed`, клиенту «Не удалось создать платёж, попробуйте ещё раз».

Частичный уникальный индекс должен покрывать и `creating`, и `pending`, чтобы исключить две параллельные заявки.

### 7.3. Статусы заявки
| Статус | Смысл | В конверсии |
|---|---|---|
| `creating` | создана, QR ещё не получен | нет |
| `pending` | QR выдан, ждём оплату | нет |
| `paid` | оплачена, USDT зачислены | да, успех |
| `expired` | истёк срок | да, неуспех |
| `cancelled` | отменена клиентом | да, неуспех |
| `failed` | провайдер не выдал QR | нет |
| `review` | требует решения админа | нет, пока не решена |
| `rejected` | админ отклонил после разбора | да, неуспех |

Разрешённые переходы:
```
creating → pending | failed
pending  → paid | expired | cancelled | review
expired  → review (callback об оплате пришёл после закрытия)
cancelled→ review (callback об оплате пришёл после закрытия)
review   → paid | rejected
```
Любой иной переход — ошибка `InvalidTransition`. Переходы реализовать одной функцией с таблицей переходов.

Заявки `creating`, зависшие дольше 2 минут (процесс упал между шагами 4 и 6), фоновая задача переводит в `failed`.

### 7.4. Платёжный провайдер
Интерфейс в `payments/base.py`:
```python
@dataclass(frozen=True)
class QrPayment:
    provider_payment_id: str
    qr_url: str               # ссылка формата НСПК: https://qr.nspk.ru/...
    expires_at: datetime
    raw: dict

@dataclass(frozen=True)
class CallbackEvent:
    event_key: str            # уникальный ключ события для идемпотентности
    provider_payment_id: str
    status: Literal["paid", "failed", "expired"]
    amount_rub: int | None
    payer_info: dict | None
    raw: dict

class PaymentProvider(Protocol):
    name: str
    async def create_qr(self, *, order_public_id: str, amount_rub: int,
                        ttl_seconds: int, description: str) -> QrPayment: ...
    async def get_status(self, provider_payment_id: str) -> CallbackEvent | None: ...
    def verify_callback(self, headers: Mapping[str, str], body: bytes) -> bool: ...
    def parse_callback(self, body: bytes) -> CallbackEvent: ...
```

`MockProvider`:
- `create_qr` возвращает ссылку вида `https://qr.nspk.ru/MOCK<uuid>?type=02&bank=100000000000&sum=<копейки>&cur=RUB&crc=0000`;
- подпись callback — HMAC-SHA256 тела секретом `MOCK_PROVIDER_SECRET` в заголовке `X-Signature`;
- `get_status` возвращает состояние из внутренней таблицы mock-платежей;
- в админке при `PAYMENT_PROVIDER=mock` у заявки есть кнопки «Симулировать оплату» и «Симулировать оплату с другой суммой». Они формируют настоящий подписанный callback и отправляют его в общий обработчик — то есть проходят весь боевой путь.

Реального провайдера заказчик подключит позже. Описать шаги в `docs/PAYMENT_PROVIDER.md`: какой класс написать, где зарегистрировать, какие переменные добавить.

### 7.5. Обработка callback
`POST /api/payments/callback/{provider}`:
1. Прочитать сырое тело. Сохранить в `payment_callbacks` (включая невалидные).
2. `verify_callback` → при неверной подписи ответ `401`, обработка прекращается.
3. `parse_callback`. Вставка `event_key` с `ON CONFLICT DO NOTHING`; если событие уже обработано — ответить `200` и ничего не делать.
4. Найти заявку по `(provider, provider_payment_id)`. Не найдена → `200`, алерт сотрудникам.
5. В одной транзакции: `FOR UPDATE` заявки, затем `FOR UPDATE` пользователя (порядок блокировок всегда одинаковый: заявка/вывод → пользователь).
6. Для `status == "paid"`:
   - заявка уже `paid` → ничего;
   - `amount_rub` из callback не равен `orders.amount_rub` → `review`, причина `amount_mismatch`, **без зачисления**;
   - заявка `pending` → зачислить;
   - заявка `expired` или `cancelled` → `review`, причина `paid_after_close`, **без зачисления**, алерт сотрудникам.

   Поздней оплаты как сценария нет: QR перестаёт действовать через `order_ttl_minutes` (15 минут), этот же срок передаётся провайдеру в `ttl_seconds`. Ветка `paid_after_close` — только страховка на случай, когда клиент оплатил в срок, а callback от провайдера задержался или потерялся и сверка перед истечением его не поймала. Автоматического зачисления в этом случае нет, решает админ.
7. Зачисление: проводка `deposit` на `usdt_amount`, `users.balance += usdt_amount`, `status=paid`, `paid_at`, `finished_at`, уведомление в outbox, пересчёт антифрода.
8. Ответ `200` только после коммита. При внутренней ошибке — `500`, чтобы провайдер повторил.

**Сверка перед истечением**: фоновая задача перед переводом `pending → expired` вызывает `provider.get_status`. Если платёж прошёл, а callback потерялся — заявка проводится как оплаченная тем же кодом, что и callback.

**Решение по `review`** принимает админ: «Зачислить по курсу заявки», «Зачислить по текущему курсу» (пересчёт от `paid_amount_rub`), «Отклонить» (с комментарием; возврат рублей плательщику — вне системы). Всё пишется в аудит.

## 8. Выводы

### 8.1. Создание
Одна транзакция, `FOR UPDATE` пользователя:
- проверки из 6.5; идемпотентность по `idempotency_key`;
- `fee` по сети на момент создания; `amount_to_send = amount − fee`; обязательно `amount_to_send > 0`;
- проводка `withdrawal_hold`: `balance −= amount`, `hold += amount`;
- статус `pending`; уведомление в служебный чат; запуск правил антифрода для выводов.

### 8.2. Статусы
```
pending     → in_progress (оператор взял) | cancelled (клиент) | rejected
in_progress → verifying (внесён хэш) | rejected | pending (оператор вернул в очередь)
verifying   → completed (проверка прошла) | in_progress (проверка не прошла, нужен другой хэш)
```
- `rejected` и `cancelled`: проводка `withdrawal_release` (`hold −= amount`, `balance += amount`). Причина отклонения обязательна и показывается клиенту.
- `completed`: проводка `withdrawal_complete` (`hold −= amount`).
- «Взять в работу» — атомарно (`UPDATE ... WHERE status='pending'`), чтобы два оператора не взяли одну заявку.
- Заявки с `amount ≥ withdraw_admin_only_from_usdt` закрывать может только админ.

### 8.3. Валидация адресов (`chains/addresses.py`)
- **TRC-20**: Base58Check. 34 символа, начинается с `T`, после декодирования 25 байт, первый байт `0x41`, контрольная сумма — первые 4 байта двойного SHA-256. Base58 реализовать самостоятельно (30 строк), без сторонней библиотеки.
- **BEP-20**: `0x` + 40 hex-символов. Если адрес в смешанном регистре — проверить контрольную сумму EIP-55 (keccak-256 из pycryptodome); полностью нижний или верхний регистр допускается. Хранить в EIP-55.
- Отдельно проверять, что клиент не ввёл адрес контракта USDT и не нулевой адрес.

### 8.4. Проверка хэша транзакции
Оператор вносит хэш → нормализация (trim, нижний регистр; для TRON убрать префикс `0x`, 64 hex; для BSC `0x` + 64 hex) → проверка уникальности → статус `verifying` → проверка в блокчейне.

Интерфейс:
```python
@dataclass(frozen=True)
class TransferInfo:
    found: bool
    success: bool
    confirmations: int
    token_contract: str | None
    to_address: str | None
    amount: Decimal | None        # уже с учётом decimals
    block_time: datetime | None

class ChainVerifier(Protocol):
    async def get_usdt_transfer(self, tx_hash: str, expected_to: str) -> TransferInfo: ...
    def explorer_url(self, tx_hash: str) -> str: ...
```

**TRC-20**
- Контракт USDT: `TR7NHqjeKQxGTCi8q8ZY4pL8otSzgjLj6t`, decimals = 6.
- Запросы к TronGrid: `POST {TRON_API_URL}/walletsolidity/gettransactioninfobyid` с телом `{"value": "<txid>"}` (подтверждённые данные; `receipt.result == "SUCCESS"`), и `GET {TRON_API_URL}/v1/transactions/<txid>/events` (события `Transfer` с полями `from`, `to`, `value`, `contract_address`).
- Если задан `TRON_API_KEY`, передавать заголовок `TRON-PRO-API-KEY`.
- Адреса в ответах могут быть в hex-формате (`41…` или `0x…`) — привести к Base58 перед сравнением.
- Транзакция найдена в solidity-узле → считается подтверждённой.
- Ссылка: `https://tronscan.org/#/transaction/<hash>`.

**BEP-20**
- Контракт USDT: `0x55d398326f99059fF775485246999027B3197955`, decimals = 18.
- JSON-RPC: `eth_getTransactionReceipt` и `eth_blockNumber`.
- `status == 0x1`; в `logs` найти запись, где `address` = контракт USDT, `topics[0]` = `0xddf252ad1be2c89b69c2b068fc378daa952ba7f163c4a11628f55a4df523b3ef`, `topics[2]` = адрес получателя (дополненный до 32 байт); `data` = сумма.
- Подтверждений нужно ≥ 15 (`blockNumber_now − blockNumber_tx`).
- Время блока — через `eth_getBlockByNumber`.
- RPC из списка `BSC_RPC_URLS` перебираются по очереди при ошибке.
- Ссылка: `https://bscscan.com/tx/<hash>`.

Точные форматы ответов **сверить с официальной документацией** TronGrid и BSC; для тестов сохранить фикстуры реалистичных ответов.

**Результаты проверки** (`verify_status`):
| Код | Условие | Действие |
|---|---|---|
| `ok` | всё совпало | → `completed` |
| `not_found` | транзакция не найдена | оставить `verifying`, повторять; через 30 минут → `in_progress` с ошибкой |
| `pending_confirmations` | найдена, мало подтверждений | оставить `verifying`, повторять |
| `tx_failed` | транзакция неуспешна | → `in_progress`, показать оператору |
| `wrong_token` | нет перевода USDT по нужному контракту | → `in_progress` |
| `wrong_recipient` | получатель не совпадает | → `in_progress` |
| `wrong_amount` | сумма ≠ `amount_to_send` (сравнение точное) | → `in_progress` |
| `too_old` | транзакция раньше создания вывода | → `in_progress` |
| `duplicate_hash` | хэш уже использован | отказ сразу, статус не меняется |
| `explorer_unavailable` | API недоступен | оставить `verifying`, повторять |

Оператору показывается, что именно не сошлось: ожидаемое и фактическое значение, ссылка на эксплорер.
Фоновая задача перепроверяет `verifying` каждые 30 секунд.

**Принудительное закрытие**: только админ, с обязательным комментарием; `forced = true`; запись в аудит; алерт в служебный чат.

## 9. Антифрод

Правила — чистые функции в `domain/antifraud.py`, на вход получают данные, на выход — список срабатываний. Пересчёт запускается при каждом финальном переходе заявки и при создании вывода. Срабатывания пишутся в `antifraud_events`; повторное срабатывание того же правила без изменения ситуации не дублирует событие и алерт.

Антифрод применяется, если `settings.af_enabled` и `users.af_enabled`. Учитываются только заявки, завершённые после `users.af_reset_at`.

«Завершённые» заявки: `paid`, `expired`, `cancelled`, `rejected`. Успешные — `paid`.

### 9.1. Основные правила (заданы заказчиком, включены)
| № | Правило | Условие | Действие |
|---|---|---|---|
| A1 | Низкая конверсия | среди последних `af_window_orders` (30) завершённых заявок их не меньше `af_min_orders` (10) и конверсия < `af_min_conversion_pct` (80 %) | `can_create_orders=false`, событие `block`, алерт |
| A2 | Серия неоплат — подозрение | последние `af_streak_suspicious` (3) завершённые заявки подряд неуспешные | `is_suspicious=true`, событие `suspicious`, алерт. Создание заявок не отключается |
| A3 | Серия неоплат — блокировка | последние `af_streak_block` (5) завершённых подряд неуспешные | `can_create_orders=false`, событие `block`, алерт |

Блокировка антифродом **не затрагивает вывод** уже купленных средств.
Клиенту при попытке создать заявку: «Создание заявок приостановлено. Обратитесь в поддержку».

**Разблокировка** — только админ вручную: `can_create_orders=true`, `is_suspicious=false`, `af_reset_at=now()`, события помечаются решёнными, запись в аудит с комментарием. Без `af_reset_at` клиент был бы заблокирован повторно первой же заявкой.

Флаг `is_suspicious` автоматически не снимается.

### 9.2. Дополнительные правила
Каждое имеет свой выключатель и параметры в `settings`.

| № | Правило | По умолчанию | Параметры | Действие |
|---|---|---|---|---|
| B1 | Одна активная заявка | вкл | — | отказ в создании |
| B2 | Лимит частоты заявок | вкл | 5 в час, 15 в сутки | отказ с указанием, когда можно снова |
| B3 | Нарастающий кулдаун после неоплат | вкл | 2 подряд → 5 мин, 3 → 15 мин, 4 → 60 мин | отказ до истечения паузы |
| B4 | Общий адрес вывода у разных клиентов | вкл | — | `is_suspicious` обоим, алерт |
| B5 | Чёрный список адресов | вкл | таблица | отказ в выводе |
| B6 | Крупный вывод только через админа | вкл | от 5000 USDT | оператор не может закрыть |
| B7 | Несовпадение суммы оплаты | вкл | — | заявка в `review` (раздел 7.5) |
| B8 | Глобальная просадка конверсии | вкл, только алерт | за 60 мин ≥ 20 завершённых и конверсия < 40 % | алерт; опция `b8_auto_pause` выключает покупки |
| B9 | Сниженные лимиты для новичков | **выкл** | до 3 оплаченных заявок: макс. 20 000 ₽ за заявку, 50 000 ₽ в сутки | ограничение суммы |
| B10 | Суточный лимит оборота клиента | **выкл** | ₽ в сутки, глобально и индивидуально | отказ |
| B11 | Холд на вывод после покупки | **выкл** | N часов | свежекупленные USDT недоступны к выводу |
| B12 | Быстрый транзит | **выкл** | вывод ≥ 90 % баланса в течение 10 мин после покупки | `is_suspicious`, алерт |
| B13 | Много разных плательщиков | **выкл**, ждёт данных провайдера | > 3 разных плательщиков за 30 дней | `is_suspicious`, алерт |
| B14 | Суточный лимит вывода | **выкл** | USDT в сутки | отказ |

**Управление из админки.** Все правила B1–B14, включая выключенные по умолчанию, выводятся в разделе «Настройки → Антифрод» отдельными карточками: переключатель «включено / выключено», поля параметров, краткое описание правила на русском. Включение выключенного правила не требует правок кода или перезапуска и начинает действовать сразу. Изменения доступны только админу и пишутся в аудит. Для каждого правила есть тест в обоих состояниях: выключено — не срабатывает при выполненном условии, включено — срабатывает.

B11 реализовать через расчёт «доступно к выводу = balance − сумма депозитов за последние N часов», без отдельного типа проводок.
B13 зависит от `payer_info`; пока провайдер-заглушка его не отдаёт, правило написать и покрыть тестом, но оставить выключенным.

### 9.3. Глобальные рубильники
`purchases_enabled` и `withdrawals_enabled` — переключатели в админке (только админ), с подтверждением и записью в аудит.

## 10. Статистика

### 10.1. По клиенту
За всё время и **в разбивке по дням (МСК)**:
- заявок создано; оплачено; истекло; отменено; отклонено; в разборе;
- **конверсия общая** = оплачено / завершено;
- **конверсия по дням**;
- конверсия в окне антифрода (последние 30 завершённых) и текущая серия неоплат подряд;
- оборот в ₽ (оплаченные), получено USDT, маржа сервиса в ₽;
- средний чек, медианное время от создания до оплаты;
- выводы: количество, сумма, уплаченные комиссии;
- даты первой и последней сделки.

### 10.2. Дашборд сервиса
За сегодня, вчера, 7 и 30 дней, плюс таблица по дням:
- оборот ₽, выдано USDT, маржа ₽, число заявок, конверсия;
- новые клиенты, активные клиенты;
- выводы: в очереди (число и сумма), исполнено за период, собрано комиссий;
- суммарные обязательства: сумма `balance` и `hold` всех клиентов;
- текущий курс, его источник и возраст;
- число клиентов, заблокированных антифродом, и подозрительных.

Статистика считается SQL-запросами по требованию. Предагрегация не нужна; нужны индексы из раздела 4.

### 11.2. Добавление сотрудников
- **Суперадмины** задаются в `SUPERADMIN_TG_IDS`, при старте создаются или активируются в `staff` с `is_superadmin=true`. Через интерфейс их нельзя удалить, понизить или деактивировать.
- **Добавление по Telegram ID**: запись активна сразу.
- **Добавление по @username**: Telegram не позволяет узнать ID по нику, пока человек не написал боту. Поэтому:
  - если пользователь с таким ником уже есть в `users` — берётся его `tg_id`, запись активна сразу;
  - иначе создаётся приглашение (`tg_id = null`, `invite_expires_at = now + 48 ч`). Когда человек с этим ником (сравнение без учёта регистра) напишет боту `/start`, запись привязывается к его `tg_id`, пригласившему уходит уведомление.
  - После привязки авторитетен **только `tg_id`**; смена ника доступ не даёт и не отнимает.
- Админ не может изменить собственную роль и деактивировать себя.
- Деактивация сотрудника мгновенно отзывает все его сессии.
- Все операции — в аудит и алертом в служебный чат.

### 11.3. Вход в админку
**Внутри Telegram (Mini App)** — по `initData` (раздел 12.1); доступ есть, если `tg_id` найден в активных `staff`. Команда `/admin` в боте отправляет сотруднику кнопку открытия админского Mini App; не сотруднику бот на `/admin` не отвечает ничем особенным (как на неизвестную команду).

**В браузере** — логин + пароль + TOTP:
- логин и пароль сотрудник задаёт себе сам в админском Mini App (раздел «Профиль → Веб-доступ»). Пароли никто никому не пересылает;
- там же включается TOTP: показывается QR и секрет, включение подтверждается вводом кода;
- **без включённого TOTP вход в браузере невозможен**;
- пароль — минимум 12 символов, хранится как argon2id;
- защита от перебора: 5 неудачных попыток на логин или IP за 15 минут → блокировка на 15 минут; ответ на неверный логин и неверный пароль одинаковый;
- код TOTP нельзя использовать повторно в пределах его окна.

## 12. HTTP API

Префикс `/api`. JSON. Ошибки в едином формате `{"error": {"code": "...", "message": "..."}}` с русским `message`, пригодным для показа.
Суммы в JSON передаются **строками** (`"9.50"`), не числами.

### 12.1. Авторизация Mini App
`POST /api/auth/telegram` c телом `{"init_data": "<Telegram.WebApp.initData>", "scope": "client" | "admin"}`.

Проверка `initData` (строго по документации Telegram):
1. Разобрать строку как query string, извлечь `hash`.
2. Остальные пары отсортировать по ключу, склеить `key=value` через `\n` — это `data_check_string` (значения — после URL-декодирования).
3. `secret_key = HMAC_SHA256(key="WebAppData", msg=BOT_TOKEN)`.
4. `expected = hex(HMAC_SHA256(key=secret_key, msg=data_check_string))`.
5. Сравнить с `hash` через `hmac.compare_digest`.
6. `auth_date` не старше 10 минут.
7. Из поля `user` (JSON) взять `id`.

Успех → создаётся сессия, возвращается непрозрачный токен (32 случайных байта, base64url). В БД хранится только SHA-256 токена.
- Клиентская сессия: 12 часов, продлевается при активности.
- Сессия сотрудника: 8 часов, простой не более 60 минут.
- Токен передаётся в заголовке `Authorization: Bearer <token>`. **Cookie не используются** — это снимает вопрос CSRF.
- Фронтенд хранит токен только в памяти; при `401` повторяет авторизацию по `initData` (в Mini App) или показывает форму входа (в браузере).

`POST /api/auth/password` (`login`, `password`, `totp`) → сессия сотрудника.
`POST /api/auth/logout` → отзыв сессии.

## 13. Фронтенд

Общее для обоих приложений:
- при старте `Telegram.WebApp.ready()` и `expand()`; цвета из темы Telegram;
- подтверждения денежных действий — отдельным экраном или `showConfirm`;
- кнопка отправки блокируется на время запроса; `Idempotency-Key` генерируется один раз на попытку (UUID) и переиспользуется при повторе;
- состояния загрузки, пустого списка и ошибки есть на каждом экране;
- вёрстка работает на ширине 320 px.

### 13.1. Клиентский Mini App (`/app/`)
Минималистичный интерфейс, 5 экранов:
1. **Главная**: баланс (доступно / в обработке), курс с учётом наценки, кнопки «Купить» и «Вывести», баннер активной заявки, баннер при приостановке заявок.
2. **Покупка**: поле суммы (цифровая клавиатура, только целые), быстрые суммы 1000 / 5000 / 10 000 / 50 000, живой расчёт USDT → подтверждение → экран оплаты: QR, кнопка «Оплатить» (`Telegram.WebApp.openLink(qr_url)`), таймер, статус с автообновлением, «Отменить».
3. **Вывод**: сеть → адрес (вставка из буфера) → сумма («Всё») → предпросмотр → подтверждение.
4. **История**: лента, статусы цветом, раскрытие деталей, ссылка на эксплорер у выводов.
5. **Регистрация**: экран-заглушка для нового пользователя.

### 13.2. Админка (`/admin/`)
Одно приложение. Внутри Telegram входит по `initData`; в браузере показывает форму логин / пароль / TOTP. Адаптивная: на телефоне — нижняя навигация и карточки, на десктопе — боковое меню и таблицы.

Разделы:
- **Выводы** (стартовый экран оператора): вкладки «Очередь», «В работе у меня», «На проверке», «Завершённые». Карточка: клиент, сеть, адрес и сумма к отправке с кнопками копирования, форма ввода хэша, результат проверки с расхождениями, ссылка на эксплорер, отклонение с причиной.
- **Заявки**: фильтры, карточка, решение по `review`, симуляция оплаты (mock).
- **Клиенты**: поиск по ID, нику, номеру заявки; фильтры «подозрительные», «заблокированы антифродом». Карточка: профиль, балансы, статистика общая и по дням, заявки, выводы, проводки, события антифрода, действия админа.
- **Дашборд** (админ).
- **Антифрод**: лента нерешённых событий.
- **Настройки** (админ): все ключи из 3.2 и раздела 9, рубильники, ручной курс, чёрный список.
- **Сотрудники** (админ): список, добавление по ID или @username, роль, деактивация, статус приглашения.
- **Аудит**.
- **Профиль**: веб-доступ, TOTP, выход.

## 14. Фоновые задачи

Простой планировщик на asyncio в процессе приложения. Каждая задача:
- обёрнута в try/except — исключение логируется, цикл продолжается;
- берёт `pg_try_advisory_lock` со своим ключом, чтобы не выполняться параллельно сама с собой;
- обновляет отметку «последний успешный запуск» (для `/readyz` и алертов).

| Задача | Период | Что делает |
|---|---|---|
| `refresh_rate` | `rate_ttl_seconds` | раздел 7.1 |
| `expire_orders` | 20 с | сверка с провайдером и перевод просроченных в `expired`; редактирование сообщения с QR; пересчёт антифрода |
| `fail_stuck_creating` | 60 с | `creating` старше 2 минут → `failed` |
| `verify_withdrawals` | 30 с | раздел 8.4 |
| `send_notifications` | 2 с | отправка из outbox с повторами |
| `expire_invites` | 10 мин | удаление просроченных приглашений сотрудников |
| `check_ledger_invariant` | 1 ч | сверка балансов с проводками; расхождение → критический алерт и автоматическое выключение `withdrawals_enabled` |
| `cleanup` | 1 сутки | чистка `tg_updates`, старых `rates`, истёкших сессий |
| `global_conversion_watch` | 5 мин | правило B8 |

## 15. Безопасность и надёжность — чек-лист

**Деньги**
- [ ] Любое изменение баланса — только через `services/ledger.py`, в транзакции, с `SELECT ... FOR UPDATE` пользователя.
- [ ] Единый порядок блокировок: сначала заявка или вывод, потом пользователь.
- [ ] `CHECK (balance >= 0)`, `CHECK (hold >= 0)` в БД.
- [ ] Уникальные индексы: депозит на заявку, хэш на сеть, активная заявка на пользователя, `event_key` callback, `idempotency_key`.
- [ ] Внешние HTTP-вызовы — никогда внутри транзакции БД.

**Доступ**
- [ ] `initData` проверяется по подписи и свежести; `tg_id` берётся только из проверенных данных.
- [ ] Права проверяются на бэкенде в каждом админском эндпоинте.
- [ ] Клиент видит только свои объекты.
- [ ] Webhook Telegram защищён секретным заголовком, callback провайдера — подписью.
- [ ] Rate-limit: вход по паролю; `POST /orders`, `/withdrawals` — 10 запросов в минуту на пользователя; общий лимит 120 запросов в минуту на сессию.
- [ ] CORS закрыт (фронтенд на том же домене). Заголовки: `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, CSP с разрешением `telegram.org` для скрипта и встраивания в Telegram (`frame-ancestors`).
- [ ] Секреты только из окружения; `.env` в `.gitignore`; в логах нет токенов, паролей, `initData`, TOTP.

**Устойчивость**
- [ ] Глобальные обработчики исключений в FastAPI, в обработке апдейтов, в фоновых задачах.
- [ ] Таймауты на всех внешних запросах; повторы с задержкой.
- [ ] Миграции Alembic применяются при старте контейнера до запуска приложения.

## 16. Тесты

Backend-тесты идут на **реальном PostgreSQL** (не SQLite: нужны блокировки строк, частичные индексы, advisory locks). Подключение через `TEST_DATABASE_URL`; каждый тест — в чистой схеме или в откатываемой транзакции. Все внешние HTTP замоканы (respx); тесты не ходят в сеть. Telegram подменяется фейковым сервером, который записывает исходящие вызовы.

Цель покрытия: `app/domain` и `app/services` ≥ 90 %, backend в целом ≥ 80 %.

### 16.1. Модульные (чистая логика)
- **Расчёт**: контрольный пример (1000 ₽, 5 %, 100 → 9.50); округление всегда вниз; наценка 0 % и дробная; property-тест (hypothesis): `usdt × rate ≤ amount × (1 − markup)` и результат ≥ 0.
- **Парсинг суммы**: `1000`, `10 000`, `1000.50`, `1000,5`, `abc`, `-100`, `0`, пустая строка, границы 999 / 1000 / 100000 / 100001, очень длинное число.
- **Адреса**: валидные и невалидные TRC-20 (длина, префикс, контрольная сумма); BEP-20 (длина, hex, EIP-55 верный и неверный, нижний регистр); адрес контракта и нулевой адрес.
- **Нормализация хэша** для обеих сетей.
- **`initData`**: валидная подпись; изменённое поле; чужой токен; просроченный `auth_date`; отсутствие `hash`; иной порядок полей.
- **Антифрод**, каждое правило отдельно:
  - A1: 9 завершённых при конверсии 0 % → не срабатывает; 10 завершённых, 7 оплачено → срабатывает; 10 завершённых, 8 оплачено → нет; в окно попадают только последние 30; заявки до `af_reset_at` не учитываются;
  - A2 и A3: 2, 3, 4, 5 неоплат подряд; оплата сбрасывает серию; `failed` и `review` серию не меняют;
  - антифрод выключен глобально и у клиента;
  - B2, B3, B4, B6, B9–B14 — срабатывание и несрабатывание.
- **Автомат статусов** заявок и выводов: все разрешённые переходы проходят, все запрещённые бросают исключение.
- **Парсер курса**: корректный ответ; нет пары USDT/RUB; нулевой курс; не JSON; число не теряет точность.

### 16.2. Интеграционные (сервисы + БД)
- **Заявка**: успешное создание; отказ при активной заявке; повтор с тем же `Idempotency-Key` возвращает ту же заявку; ошибка провайдера → `failed`; устаревший курс → отказ; `can_create_orders=false` → отказ; индивидуальные лимиты клиента.
- **Callback**: успешное зачисление; **тот же callback дважды** → одно зачисление; **два одинаковых callback параллельно** (`asyncio.gather`) → одно зачисление; неверная подпись → `401` без изменений; неизвестный платёж; несовпадение суммы → `review`; callback об оплате по истёкшей заявке → `review` без зачисления; callback об оплате по отменённой заявке → `review` без зачисления.
- **Истечение**: просроченная заявка → `expired`; провайдер при сверке говорит «оплачено» → `paid`.
- **Вывод**: создание и hold; сумма больше баланса → отказ; ниже минимума → отказ; **два параллельных вывода на весь баланс** → проходит один; отмена клиентом возвращает средства; отклонение возвращает средства; завершение списывает hold; два оператора одновременно берут одну заявку → успех у одного.
- **Проверка хэша** (на фикстурах ответов TronGrid и BSC RPC): по одному тесту на каждый код из таблицы 8.4 для обеих сетей; повторное использование хэша; переключение на запасной RPC.
- **Журнал проводок**: после случайной последовательности операций инвариант 4.4 выполняется; баланс не уходит в минус; корректировка не даёт отрицательный баланс.
- **Антифрод сквозной**: 5 неоплаченных заявок подряд → клиент заблокирован, событие создано, алерт в outbox, новая заявка отклоняется; разблокировка админом → следующая заявка создаётся и повторной блокировки нет.
- **Сотрудники**: добавление по ID; приглашение по нику и привязка при `/start`; просроченное приглашение; нельзя удалить суперадмина; деактивация отзывает сессии.
- **Авторизация**: парольный вход без TOTP невозможен; блокировка после 5 неудач; повтор TOTP-кода отклоняется; истёкшая и отозванная сессия → `401`.
- **Права**: параметризованный тест по всем админским эндпоинтам — без сессии `401`, с клиентской сессией `403`, оператору на админские действия `403`.
- **Изоляция**: клиент A не видит заявки и выводы клиента B (`404`).
- **Статистика**: на подготовленном наборе данных проверить общие и дневные цифры, включая границу суток по МСК.

### 16.3. Бот (через фейковый Telegram)
- полный сценарий: `/start` → регистрация → покупка → симуляция оплаты → баланс → вывод → оператор вносит хэш → клиент получает уведомление;
- ввод суммы с копейками → подсказка, состояние сохраняется;
- `/cancel` в середине сценария;
- рестарт между шагами (новый экземпляр приложения, та же БД) — диалог продолжается;
- повторный апдейт с тем же `update_id` игнорируется;
- двойное нажатие «Подтвердить» → одна заявка;
- callback с чужим id заявки → отказ;
- `429` от Telegram → повтор после `retry_after`; `403` → `bot_blocked`;
- webhook с неверным секретом → `403`;
- исключение в хендлере не роняет обработку следующих апдейтов.

### 16.4. Фронтенд
- `tsc --noEmit` и сборка обоих приложений без ошибок;
- vitest: форматирование сумм, валидация поля суммы, API-клиент (повторная авторизация при `401`, переиспользование `Idempotency-Key`);
- один smoke-тест Playwright на приложение с подменённым `window.Telegram.WebApp` и замоканным API: клиент проходит покупку до экрана QR; оператор открывает очередь выводов. (Chromium в среде уже установлен, `playwright install` не запускать.)

### 16.5. CI
`.github/workflows/ci.yml`: ruff → mypy → pytest с сервисом PostgreSQL и отчётом покрытия → сборка и тесты фронтенда. Запуск на каждый push.

## 17. Развёртывание

`docker-compose.yml`:
- `caddy` — порты 80 и 443, автоматический сертификат Let's Encrypt; маршруты: `/api/*`, `/tg/*`, `/healthz`, `/readyz` → `app`; `/app/*` и `/admin/*` — статика фронтенда;

- `postgres` — с томом, healthcheck, не опубликован наружу;
- `backup` — ежедневный `pg_dump` в том.

`docker-compose.dev.yml` — локальный запуск без Caddy, `BOT_MODE=polling`, mock-провайдер.

**Почему нужен домен и HTTPS**: Telegram открывает Mini App только по `https://`. Поэтому в проде обязательно: сервер (VPS) с публичным IP и домен, направленный на него. Раз HTTPS уже есть, бот в проде работает через webhook.

`README.md` — пошаговая инструкция для человека без технической подготовки:
1. создать бота в @BotFather, получить токен;
2. арендовать VPS (Ubuntu 22.04+, 2 ГБ RAM), установить Docker;
3. купить домен, создать A-запись на IP сервера;
4. скопировать `.env.example` в `.env`, заполнить (каждая переменная объяснена);
5. `docker compose up -d`;
6. написать боту `/start`, затем `/admin`;
7. как узнать свой Telegram ID; как добавить сотрудников; как включить веб-вход;
8. как смотреть логи, обновлять, восстанавливать из резервной копии.

При старте приложение само выставляет webhook, команды бота и кнопку меню с адресом Mini App.

Команды `cli.py`: `check-config`, `set-webhook`, `delete-webhook`, `check-ledger`, `create-staff --tg-id --role`.

## 18. Что является заглушкой и что нужно сверить

| Блок | Состояние | Что сделать |
|---|---|---|
| KYC и регистрация | заглушка «пройдено» | интерфейс `KycProvider`, `docs/KYC.md` |
| Платёжный провайдер | `MockProvider` | интерфейс `PaymentProvider`, `docs/PAYMENT_PROVIDER.md` |
| Данные плательщика (правило B13) | нет данных | правило написано, выключено |
| Парсер Rapira | формат ответа сверен с живым (раздел 7.1) | сохранить живой ответ как фикстуру |
| Форматы TronGrid и BSC RPC | хосты доступны, базовые запросы отвечают; ответы по конкретным транзакциям не сверялись | сверить на реальных транзакциях USDT, сохранить ответы как фикстуры |

**Важно про сеть.** В облачной среде разработки «K-USDT» сетевой доступ ограничен списком. В него добавлены `api.rapira.net`, `api.trongrid.io`, `bsc-dataseed.binance.org` — они доступны. Остальные внешние адреса (включая `api.telegram.org` и запасной RPC `bsc-dataseed1.defibit.io`) закрыты: прокси отвечает `403`. Поэтому:
- если нужен ещё один хост — не пытайся обходить ограничение, запроси доступ у владельца или работай на фикстурах;
- живой бот в этой среде не запустится (нет доступа к Telegram) — сквозные сценарии проверяются на фейковом Telegram-сервере;
- автотесты в любом случае не ходят в сеть;
- напиши `scripts/check_external.py`: скрипт делает по одному живому запросу в Rapira, TronGrid и BSC RPC, печатает разобранный результат и явно сообщает, совпал ли формат с ожидаемым. Владелец запустит его на сервере;
- парсеры пиши терпимыми к лишним полям и строгими к отсутствию нужных; при несовпадении формата — понятная ошибка в логе и алерт, а не падение.

В итоговом отчёте честно перечисли, что проверено на живых данных, а что только на фикстурах.

## 20. Критерии приёмки

1. `docker compose -f docker-compose.dev.yml up` поднимает рабочий сервис с mock-провайдером.
2. Сквозной сценарий проходит и в боте, и в клиентском Mini App: регистрация → покупка на 1000 ₽ → симуляция оплаты → зачисление по формуле → вывод → оператор вносит хэш → проверка → уведомление клиенту.
3. Повторный и параллельный callback не приводят к двойному зачислению (есть тесты).
4. Параллельные выводы не уводят баланс в минус (есть тест).
5. Антифрод: 3 неоплаты подряд — флаг «подозрительный»; 5 подряд — блокировка создания заявок; конверсия ниже 80 % на последних 30 при минимум 10 завершённых — блокировка; после ручной разблокировки повторной мгновенной блокировки нет.
6. Наценка меняется индивидуально, новая заявка считается по новой наценке, старые не пересчитываются.
7. Статистика клиента показывает общую конверсию и конверсию по дням.
8. Неверный хэш (не та сумма, не тот получатель, не тот токен, повторный, несуществующий) не закрывает вывод; оператор видит причину.
9. Сотрудник добавляется по Telegram ID и по @username; оператор не может выполнить админские действия ни через интерфейс, ни прямым запросом к API.
10. Админка открывается и как Mini App, и в браузере (логин + пароль + TOTP).
11. В коде нет библиотек для Telegram-ботов.
12. Все тесты, ruff, mypy и сборка фронтенда проходят; покрытие не ниже целевого.
13. `README.md` позволяет развернуть сервис по шагам; в `docs/DECISIONS.md` записаны все отклонения от ТЗ; в отчёте указано, что не проверено на живых данных.
